## Actions 第三次修复 + 真正根因（bun symlink → copyfile）
- 第三次 push b941f60c 仍全红，但已过 install 阶段（4024 packages installed），挂在 `tsc -b`：`Cannot find module '@mercurjs/admin' / '@medusajs/framework/http'` + `Cannot find type definition file for 'node'`。
- **真正根因**：bun 默认把包装成指向 `node_modules/.bun/` store 的 **symlink**。多阶段 Docker 里 `COPY --from=deps /app/node_modules` 把 symlink 拷过去但 store 跨阶段脆弱，导致 builder 阶段模块解析断（react 也是 symlink 却没断，是 .bun 部分未带走）。本地能 build 是因为 store 在本地存在。
- **修法**：三个 Dockerfile 的 `bun install --frozen-lockfile` 加 `--backend=copyfile`，让 node_modules 变成自包含真实文件、无 .bun store，COPY --from 不再弄断链接。已本地用迷你项目验证：copyfile 产出 REAL_DIR 且无 .bun store。
- 注意：bun `--backend` 取值是 clonefile/hardlink/symlink/copyfile（**没有 `copy`**）。bun.lock 100% 指向 registry.npmmirror.com（Carl 国内镜像），GitHub runner 在美国能连 npmmirror，注册表可达性不是问题。
- 第四次 push dd82533b 修 copyfile，run 后台观察中（copyfile 装 4024 包为真实文件，install 略慢，整体约 5-8 分钟）。

## 第五次修复：copyfile 仍不够 —— 真正根因是 bun isolated 布局的 per-workspace node_modules 没被拷进 builder
- 第四次（dd82533b）copyfile 修完**仍全红**，过了 install（4024 包），仍挂 `tsc -b`：`Cannot find module '@mercurjs/admin' / '@medusajs/framework/http'` + `TS2688 'node'`。说明 copyfile **不是**根因。
- **确诊的真正根因（本地 symlink 证据）**：bun 用 **isolated workspace 布局**——每个 workspace 的**直接依赖**放在它自己的 `<workspace>/node_modules/`（symlink 进根 `node_modules/.bun/` store），**不提升到根**。实测：
  - `apps/admin/node_modules/@mercurjs/admin` → `../../../../node_modules/.bun/@mercurjs+admin@2.2.1.../...`
  - `apps/admin/node_modules/@types/node` → `.bun`
  - `packages/api/node_modules/@medusajs/framework` → `.bun`
  - 根 `node_modules/@mercurjs/` 只有 client/dashboard-sdk/dashboard-shared/docs，**没有 admin**。
- Dockerfile builder 阶段原写 `COPY --from=deps /app/node_modules ./node_modules`（**只拷根**），漏掉 `apps/*/node_modules` 和 `packages/api/node_modules` → 那三个包在 Docker 里全找不到。本地 `bun run build` 能过是因为本地有完整 per-workspace 布局。
- **修法**：三个 Dockerfile builder 阶段改 `COPY --from=deps /app ./`（整棵 workspace 树：所有 package.json + 根 node_modules/.bun + 各 workspace node_modules，相对 symlink 全保真），再 `COPY . .` 覆盖源码（.dockerignore 已排 node_modules，不会覆盖拷来的依赖）。
- `--backend=copyfile` 保留（让 .bun store 为真实文件，COPY --from 跨阶段更稳），但**它不是本次根因**——根因是 per-workspace node_modules 没拷。
- 注意 npm vs bun 对 `run build` 的模块解析无差异（都读同一份 node_modules）；本地 `npm run build` 在完整布局下也应过。
- 第五次 push f3763ab5，run 后台观察中。
- **结果：全绿 ✅**（run 30689226266）。admin 8m34s / vendor 7m40s / api 9m1s，三个 `Build and push` 全成功，镜像推到 `ghcr.io/carlchanchina/my-mercur-{api,admin,vendor}:dev`。端到端 CI/CD 跑通：push dev → Actions 构建三镜像 → push GHCR。
- 备注：本地 `gh` token 无 `read:packages` scope，`gh api /user/packages` 查 GHCR 列表会 403（zsh 里带 `?` 的 URL 还要加引号防 glob）；但 workflow 用 `GITHUB_TOKEN`（packages:write）push 成功即证明镜像已进 GHCR。
- 遗留（非阻断）：api 镜像 production 阶段只拷根 node_modules，若 Medusa `.medusa/server` 非完全自包含，容器启动时可能也要 per-workspace node_modules——待实际部署验证。
- 经验（重要）：**bun isolated/pnpm 式 monorepo 的 Docker 多阶段构建，`COPY --from=deps` 必须拷整棵 workspace 树（或逐个拷每个 workspace 的 node_modules），只拷根 node_modules 会丢各包直接依赖**。这是 bun/pnpm 多阶段构建的经典坑，与 npm/yarn 平铺布局不同。

## 🔴 medusa db:migrate 卡死根因 + 修复（Mercur 部署核心 blocker）
- 症状：Dokploy 部署 Mercur 后 `medusa db:migrate` 打印 "Running migrations..." 后**永久卡死**，mercur_db 只有 1 张表，api-server/api-worker 崩溃循环。
- **根因（已确诊并验证修复）**：Medusa 的 `loadDatabaseConfig`→`getDefaultDriverOptions()` 对**任何非 localhost 的 DB URL 自动开启 SSL**（`driverOptions.connection.ssl = {rejectUnauthorized:false}`）。本共享 Postgres（`infradb-shared-fi5pyt_postgres`，carl 角色）**不做 SSL**，导致迁移锁连接（`lockKnex`，`modules-sdk` 的 `medusa-app.js` `applyMigration` 里 `createPgConnection({...dbData, pool:{min:1,max:1}})`）的 SSL 握手永远完不成；而 knex 的 `propagateCreateError:false` 把连接创建失败**静默吞掉** → `lockKnex.transaction(fn)` 的回调 `fn` 永不触发 → 死等。
  - 关键佐证：隔离测试 `lockKnex.transaction()` 在 `ssl:false` 下 30-100ms 完成；一旦 `ssl={rejectUnauthorized:false}` 就**卡死**（回调永不触发，PG 连接数不增）。
  - `DATABASE_DRIVER_OPTIONS='{"connection":{"ssl":false}}'` 环境变量**不生效**——`loadDatabaseConfig` 的 `isModuleServiceInitializeOptions` 分支会用 `options.database.driverOptions ?? getDefaultDriverOptions(clientUrl)` 把 env 覆盖回 ssl 对象。
- **修复（已在远程 worker 节点 192.168.10.107 实测迁移成功，表数 1→195）**：在 `DATABASE_URL` 末尾追加 `?sslmode=disable`。`getDefaultDriverOptions` 的正则含 `sslmode=(disable)`，匹配后返回 `localOptions`（`ssl:false`），且 pg 也读到 `sslmode=disable` 不协商 SSL。完整值：
  `postgres://carl:jackchen1984@infradb-shared-fi5pyt_postgres:5432/mercur_db?sslmode=disable`
- 落地动作：**Dokploy `mercur`/`infradb-plane` 栈的所有服务（api-server、api-worker、admin、vendor）的 `DATABASE_URL` 都必须带 `?sslmode=disable`**，并在 Dokploy UI 改完 env 后 redeploy/restart。 worker 节点不是 swarm manager，无法从这里改 swarm service env，需 Carl 在 Dokploy manager/UI 操作。
- 调试技法（已沉淀为 skill `medusa-migration-hang-debug`）：①把 `@medusajs/modules-sdk` 的 `medusa-app.js` 用字符串替换注入 `[DBG]` console.error 锚点（ENTER/EXIT bootstrapAll、BEFORE/AFTER createPgConnection、BEFORE transaction、INSIDE tx callback、AFTER advisory lock、concurrency-raw、dbData.clientUrl）；②挂载覆盖进镜像跑 `medusa db:migrate` 看锚点顺序定位卡点；③读 PG 容器日志 `docker logs <pg> | grep FATAL` 抓角色/连接错误；④隔离复现用 `docker run --entrypoint node` 直接 `createPgConnection` + `transaction` 测不同 driverOptions/ssl/pool。
